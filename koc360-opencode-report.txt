# Final Report: Student Client-Side Navigation Loading Fix

## 1. Affected Student Route

**File:** `src/routes/students_.$studentId.tsx`  
**Route path:** `/students_/$studentId`  
**Route name:** Student 360 / Student Profile Page

## 2. Root Cause

The route loader was calling `getStudentProfileData(params.studentId)` directly from `@/lib/students/profile.server` without wrapping it in a `createServerFn`. This caused a **server/client boundary violation** during client-side navigation.

The `.server.ts` module imports server-only dependencies (Notion API, environment variables) that are not available in the client execution context. During client-side navigation, the loader attempted to execute server-only code without proper server boundary isolation.

## 3. Why Hard Refresh Worked

During hard refresh (initial page load), TanStack Start performs **server-side rendering (SSR)**:
- The loader executes in a full Node.js server context
- All `.server.ts` modules and environment variables are available
- `getStudentProfileData()` can access Notion API and config without issues
- The page renders successfully on the server and hydrates on the client

## 4. Why Client-Side Navigation Failed

During client-side navigation (e.g., clicking a student link from the students list):
- TanStack Start attempts to re-run the loader in the client context
- Without `createServerFn` wrapper, the loader doesn't properly establish the server boundary
- The `.server.ts` module import chain tries to execute in a context where server-only dependencies are unavailable
- This causes the loader to fail or return incomplete data
- The page either shows an error state or loads with missing data

## 5. Same as Session Workspace Bug?

**Yes, this is the exact same pattern.**

Both routes had loaders that directly called `.server.ts` functions without `createServerFn` wrappers:

**Session Workspace (previously fixed):**
```typescript
loader: async ({ params }) => {
  return await getSessionWorkspaceData(params.sessionId);  // ❌ Direct call
}
```

**Student Profile (just fixed):**
```typescript
loader: async ({ params }) => {
  return await getStudentProfileData(params.studentId);  // ❌ Direct call
}
```

Both were fixed by wrapping the server function call in `createServerFn`.

## 6. Exact Fix Applied

Added a `createServerFn` wrapper for the student profile data loader:

```typescript
const loadStudentProfile = createServerFn({ method: "GET" })
  .validator((data: unknown) => {
    if (!data || typeof data !== "object" || !("studentId" in data) || typeof data.studentId !== "string") {
      throw new Error("Invalid studentId");
    }
    return data as { studentId: string };
  })
  .handler(async ({ data }) => {
    return await getStudentProfileData(data.studentId);
  });
```

Updated the route loader to call the server function:

```typescript
loader: async ({ params }) => {
  return await loadStudentProfile({ data: { studentId: params.studentId } });
}
```

This ensures proper server/client boundary isolation during both SSR and client-side navigation.

## 7. createServerFn Added/Changed

**Added:** `loadStudentProfile` server function  
**Method:** GET  
**Validator:** Validates that `studentId` is a non-empty string  
**Handler:** Calls `getStudentProfileData(data.studentId)`  
**Pattern:** Matches the existing pattern used in `sessions_.$sessionId.tsx` and other routes

3. **Generate Prompt** — Construct LLM prompt from normalized data
4. **Call LLM** — Send prompt to language model
5. **Validate Output** — Verify schema, check for hallucinations
6. **Generate Parent Version** — Transform to parent-friendly language
7. **Generate Student Version** — Transform to student-friendly language
8. **Generate PDF** — Render report to PDF format

```typescript
if (!studentId) {
  throw new Error(`No student associated with session: ${sessionId}`);
}

// Failed to fetch sessions
if (!sessionsResult.ok) {
  throw new Error(`Failed to fetch sessions: ${sessionsResult.message}`);
}
```

Graceful handling for missing optional data:
- Returns `null` for missing assessment
- Returns `null` for missing sprint
- Returns empty arrays for missing goals/tasks/recommendations
- Never throws for missing optional data

## 3. Prompt Architecture

The Prompt Builder layer converts a `ReportContext` into a complete `PromptDocument` that can be sent to any LLM provider.

### Architecture Principles

1. **Provider-Independent**: No references to OpenAI, Anthropic, Gemini, or any specific LLM provider
2. **Modular**: Each prompt section is built by a separate function
3. **Template-Driven**: Long prompt strings are stored in templates, not hardcoded in logic
4. **Composable**: Sections can be added, removed, or reordered without changing the builder
5. **Typed**: All prompt components have strict TypeScript types

### Core Types

```typescript
interface PromptDocument {
  system: string;      // System message that sets AI behavior
  user: string;        // User message containing context and request
  metadata: PromptMetadata;
  sections: PromptSection[];  // Individual sections for debugging
}

interface PromptMetadata {
  generatedAt: string;
  templateVersion: string;
  availableSources: string[];
  missingSources: string[];
  characterCount: number;
  wordCount: number;
}
```

## 4. Prompt Generation Flow

```
buildReportPrompt(context: ReportContext)
    ├── 1. Build individual sections
    │   ├── buildRoleSection(context)
    │   ├── buildStudentSection(context)
    │   ├── buildSessionNotesSection(context)
    │   ├── buildAssessmentSection(context)
    │   ├── buildGoalsSection(context)
    │   ├── buildSprintSection(context)
    │   ├── buildTasksSection(context)
    │   ├── buildRecommendationsSection(context)
    │   ├── buildDataAvailabilitySection(context)
    │   └── buildOutputSection()
    ├── 2. Sort sections by order
    ├── 3. Build system prompt from SYSTEM_PROMPT template
    ├── 4. Concatenate all sections into user prompt
    ├── 5. Build metadata (timestamp, word count, sources)
    └── 6. Return PromptDocument { system, user, metadata, sections }
```

## 5. Prompt Section Hierarchy

The prompt is organized into 10 sections, each with a specific purpose:

| Order | Section ID | Title | Purpose |
|-------|-----------|-------|---------|
| 1 | role | Role & Context | Defines the AI's role and coaching context |
| 2 | student | Student Profile | Student demographics and attention status |
| 3 | session-notes | Session Notes | Wins, challenges, core notes, commitments |
| 4 | assessment | Assessment Data | Latest assessment scores and results |
| 5 | goals | Goals | Active and completed goals with progress |
| 6 | sprint | Sprint Data | Current sprint focus and progress |
| 7 | tasks | Tasks | Overdue, upcoming, and completed tasks |
| 8 | recommendations | AI Recommendations | High-risk and pending recommendations |
| 9 | data-availability | Data Availability | Lists available and missing data sources |
| 10 | output-instructions | Output Instructions | Report structure and formatting rules |

## 6. Template Organization

All static prompt text is stored in `prompt.templates.ts`:

- **SYSTEM_PROMPT**: Defines AI behavior, critical rules, and tone (1,200+ characters)
- **ROLE_DEFINITION**: Coaching context and report audience
- **COACH_STYLE**: Strengths-based approach, evidence-based observations, growth mindset
- **REPORT_STYLE**: Structure, language, tone guidelines
- **OUTPUT_FORMAT**: Required report sections (Executive Summary, Strengths, Challenges, etc.)
- **GENERAL_RULES**: Data integrity, confidentiality, professionalism, clarity, actionability
- **PROMPT_TEMPLATE_VERSION**: "1.0.0" for tracking changes

### Template Design Principles

1. **Explicit Constraints**: Never invent facts, use only supplied data, never diagnose
2. **Professional Tone**: Educational coach, not psychologist
3. **Evidence-Based**: Ground all statements in provided data
4. **Growth-Focused**: Frame challenges as opportunities
5. **Actionable**: Every insight leads to concrete next steps

## 3. AI Architecture Summary

The AI Design Specification establishes the foundational architecture for all AI features in Koç360. It is organized into 11 major sections:

### 3.1 AI Vision
Defines AI as a **supporting actor** — it assists coaches by aggregating data, recognizing patterns, drafting reports, and surfacing risks, but **never decides, publishes, or modifies authoritative records** without explicit human action.

### 3.2 AI Principles (12 Non-Negotiable Rules)
1. Evidence-Based
2. Coach, Not Teacher
3. Coach, Not Psychologist
4. Never Hallucinate
5. Never Diagnose
6. Never Shame
7. Never Invent Missing Information
8. Explain Uncertainty
9. Encourage Growth Mindset
10. Privacy and Permission Scope
11. Auditability

### 3.3 AI Personas (7 Roles)
| Persona | Context | Responsibility |
|---------|---------|----------------|
| Session Coach | Session Workspace | Session briefings, note summaries, risk surfacing |
| Report Writer | Report Builder/Workspace | Report drafting, gap detection, quality suggestions |
| Sprint Advisor | Sprint Workspace | Sprint progress, task prioritization, risk flagging |
| Goal Reviewer | Goal Workspace | Goal progress analysis, priority recommendations |
| Parent Communication Assistant | Report Workspace | Parent-friendly report drafting |
| Command Center Briefing | Command Center | Daily prioritization and attention signals |
| Risk Analyst | Student 360, Command Center | Risk signal detection and trend analysis |

### 3.4 Report Generation Pipeline (9 Stages)
```
Collect Sources → Validate Sources → Normalize Data → Build Context → Build Prompt → Call LLM → Validate Output → Human Review → Publish
```

### 3.5 Prompt Architecture (7 Sections)
1. System Message (identity, mission, constraints)
2. Role Definition (persona, task)
3. Context (data from ReportContext)
4. Rules (AI Principles enforcement)
5. Output Instructions (format, structure, length, style)
6. Safety Rules (critical boundaries reinforcement)
7. Examples (optional, few-shot)

### 3.6 Output Strategy
**Decision:** Structured Markdown with JSON Metadata
- Human-readable Markdown for coach editing
- JSON metadata for validation and audit
- Justified by: coach-friendliness + machine-parseability

### 3.7 Validation Layer (5 Stages)
1. Schema Validation
2. Grounding Check (hallucination detection)
3. Safety Check (prohibited language scan)
4. Quality Check (tone, length, structure)
5. Confidence Scoring

### 3.8 Missing Data Strategy
- Never invent missing data
- Explicitly state "Insufficient evidence to determine [X]"
- Adjust confidence score based on data availability
- Flag missing critical data for coach attention

### 3.9 Confidence Model
Weighted formula:
```
confidence = (dataAvailability × 0.4) + (groundingQuality × 0.3) + (outputQuality × 0.2) + (safetyScore × 0.1)
```

| Range | Interpretation | Action |
|-------|----------------|--------|
| 0.9–1.0 | High confidence | Present with confidence badge |
| 0.7–0.9 | Medium confidence | Present with caution note |
| 0.5–0.7 | Low confidence | Flag for careful review |
| < 0.5 | Very low confidence | Reject and regenerate |

## 3. Provider Interface

The provider abstraction layer defines a common interface for all LLM providers:

```typescript
export interface LLMProvider {
  providerName(): string;
  generate(promptDocument: PromptDocument): Promise<PromptOutput>;
  health(): Promise<boolean>;
}

export interface LLMProviderConfig {
  apiKey: string;
  model: string;
}

export type LLMProviderName = "nvidia" | "openai" | "anthropic" | "openrouter" | "ollama";
```

### Provider Responsibilities

1. **providerName()** — Returns the provider identifier (e.g., "nvidia", "openai")
2. **generate(promptDocument)** — Accepts a PromptDocument and returns a PromptOutput with the AI response
3. **health()** — Checks if the provider is available and responsive

### Key Design Principles

- **Provider-Independent**: The application code never references specific providers
- **Environment-Driven**: Provider selection is controlled via `LLM_PROVIDER` environment variable
- **Extensible**: New providers can be added by implementing the `LLMProvider` interface
- **Type-Safe**: All provider interactions use strict TypeScript types

```typescript
export function getLLMProvider(): LLMProvider {
  const providerName = (process.env.LLM_PROVIDER || "nvidia").toLowerCase();

  switch (providerName) {
    case "nvidia": {
      const apiKey = process.env.NVIDIA_API_KEY;
      const model = process.env.NVIDIA_MODEL || "openai/gpt-oss-120b";

      if (!apiKey) {
        throw new Error("NVIDIA_API_KEY environment variable is not set");
      }

      return new NvidiaProvider({ apiKey, model });
    }

    default:
      throw new Error(`Unsupported LLM provider: ${providerName}`);
  }
}
```

## 4. ReportOutput Schema

```typescript
interface ReportOutputSummary {
  currentStatus: string;
  keyInsight: string;
  recommendedFocus: string;
}

interface ReportOutputNextSprintFocusItem {
  title: string;
  description: string;
}

interface ReportOutputConfidence {
  score: number;       // 0 to 1
  missingInformation: string[];
  suggestions: string[];
}

interface ReportOutput {
  summary: ReportOutputSummary;
  strengths: string[];
  challenges: string[];
  coachNotes: string;
  nextSprintFocus: ReportOutputNextSprintFocusItem[];
  confidence: ReportOutputConfidence;
}
```

## 5. Prompt Changes

The `OUTPUT_FORMAT` template and `buildOutputSection()` function were updated to explicitly request JSON:

**Before (markdown):**
```
## 1. EXECUTIVE SUMMARY
Brief overview...
## 2. STRENGTHS & PROGRESS
...
FORMAT: Markdown with clear headings
```

**After (JSON):**
```
Return ONLY valid JSON.
Do not wrap inside markdown.
Do not explain.
Do not add extra text.

Output MUST match this schema exactly:
{
  "summary": { "currentStatus": "...", "keyInsight": "...", "recommendedFocus": "..." },
  "strengths": ["..."],
  "challenges": ["..."],
  "coachNotes": "...",
  "nextSprintFocus": [{ "title": "...", "description": "..." }],
  "confidence": { "score": 0.85, "missingInformation": ["..."], "suggestions": ["..."] }
}
```

The PromptBuilder architecture itself was NOT modified — only the template strings changed.

## 6. NVIDIA Provider Changes

Two key changes to `NvidiaProvider`:

1. **Added `response_format`**: The API request now includes `response_format: { type: "json_object" }` which instructs the NVIDIA API to return structured JSON.

2. **Added early JSON validation**: After receiving the response, the provider attempts to `JSON.parse()` the text. If parsing fails, it throws a `ValidationError` immediately.

## 7. Validator Changes

The validator was completely rewritten. All markdown parsing was removed:

**Removed:**
- `extractMetadata()` — JSON metadata extraction from mixed text
- `parseMarkdownSections()` — Heading-based section parser
- `AIResponse` type construction from sections

**Added:**
- `validateReportOutput(output)` — Parses and validates the complete ReportOutput schema
- `validateSummary()` — Validates summary object with 3 required string fields
- `validateStringArray()` — Validates arrays of non-empty strings
- `validateString()` — Validates individual non-empty string fields
- `validateNextSprintFocus()` — Validates array of objects with title + description
- `validateConfidence()` — Validates confidence object with score (0-1), missingInformation, suggestions

All validation functions accumulate errors in a shared array and throw `ValidationError` if any errors are found.

## 8. Mapping Flow

```
ReportOutput (from validator)
          ↓
mapReportOutputToWorkspaceData(output, baseData, generatedAt)
          ↓
    ├── buildSummarySections(summary)
    │      → [
    │          { label: "Current Status", content: summary.currentStatus },
    │          { label: "Key Insight", content: summary.keyInsight },
    │          { label: "Recommended Focus", content: summary.recommendedFocus }
    │        ]
    │

    ├── challenges → output.challenges (string[])
    ├── coachNotes → output.coachNotes (string)
```

The workspace components receive the exact same props they did before. The UI does not know an AI exists.

## 10. Error Handling

### JSON Parsing Failure (in provider)
If the LLM response cannot be parsed as JSON, the NVIDIA provider throws a `ValidationError` with message "LLM response is not valid JSON".

### Schema Validation Failure (in validator)
If the JSON is valid but doesn't match the ReportOutput schema, the validator throws a `ValidationError` with specific field-level errors, e.g.:
- "summary is missing or not an object"
- "strengths[0] must be a non-empty string"
- "confidence.score must be a number between 0 and 1"

### UI Error Handling
```typescript
try {
  const output = await generateReportOutput({ data: { sessionId } });
  setReportOutput(output);
  toast.success("Report generated successfully.");
} catch (error) {
  if (error instanceof ValidationError) {
    toast.error("Report validation failed: " + error.errors.join(", "));
  } else if (error instanceof Error) {
    toast.error("Report generation failed: " + error.message);
  } else {
    toast.error("Report generation failed.");
  }
}
```

### Recovery
- On failure, the previous workspace data remains visible (no state reset)
- User can retry by clicking "Generate Again" again
- Loading state is always reset in `finally` block

## 11. Removed Markdown Logic

The following markdown-related logic was completely removed:

1. **`extractMetadata()`** in `validator.server.ts` — Extracted JSON metadata from mixed markdown/JSON text using brace counting and regex. Deleted entirely.

2. **`parseMarkdownSections()`** in `validator.server.ts` — Parsed markdown headings (`## Heading`) and extracted content between them. Deleted entirely.

3. **`transformAIResponseToWorkspaceData()`** in `report-workspace.tsx` — Mapped markdown sections to workspace data using title matching and list extraction. Replaced by `mapReportOutputToWorkspaceData()`.

4. **`extractListItems()`** in `report-workspace.tsx` — Parsed markdown list items (`- `, `* `, `1. `). No longer needed — strengths and challenges come as pre-parsed string arrays from the AI.

5. **`AIResponse` interface** in `response.types.ts` — The old response type with sections, rawMarkdown, and metadata. Replaced by `ReportOutput` in `schema.ts`.

6. **`AIResponseSection` interface** — Markdown section type. No longer needed.

7. **`rawMarkdown` field** — No response stores raw markdown anymore.

8. **`wordCount` field** — No longer tracked in response (AI doesn't return it).

9. **`reportType`, `studentId`, `sessionId`, `generatedAt`, `sourcesUsed`, `sourcesMissing`** — These metadata fields were removed from the AI response. The workspace already knows these from the loader data.

## 3. Zod Schema Design

```typescript
import { z } from "zod";

export const ReportOutputSummarySchema = z.object({
  currentStatus: z.string().min(1),
  keyInsight: z.string().min(1),
  recommendedFocus: z.string().min(1),
});

export const ReportOutputNextSprintFocusItemSchema = z.object({
  title: z.string().min(1),
  description: z.string().min(1),
});

export const ReportOutputConfidenceSchema = z.object({
  score: z.number().min(0).max(1),
  missingInformation: z.array(z.string().min(1)),
  suggestions: z.array(z.string().min(1)),
});

export const ReportOutputSchema = z.object({
  summary: ReportOutputSummarySchema,
  strengths: z.array(z.string().min(1)).min(1),
  challenges: z.array(z.string().min(1)).min(1),
  coachNotes: z.string().min(1),
  nextSprintFocus: z.array(ReportOutputNextSprintFocusItemSchema),
  confidence: ReportOutputConfidenceSchema,
});

export type ReportOutput = z.infer<typeof ReportOutputSchema>;
```

Types are inferred from Zod schemas using `z.infer<>`. The original `schema.ts` now re-exports from `report-output.schema.ts` for backward compatibility.

## 4. Validation Pipeline

The validation pipeline now has two stages:

### Stage 1: Schema Validation (Zod)

```typescript
const zodResult = ReportOutputSchema.safeParse(parsed);
if (!zodResult.success) {
  throw new ValidationError("Schema validation failed", zodErrors);
}
```

This catches:
- Missing fields
- Wrong types (string vs number, etc.)
- Empty strings where non-empty required
- Empty arrays where non-empty required
- Confidence score outside 0-1 range

### Stage 2: Business Validation

```typescript
function runBusinessValidation(output: ReportOutput): BusinessValidationIssue[] {
  // Checks for quality issues (warnings, not errors):
  // - confidence.score < 0.5 → warning
  // - strengths.length < 2 → warning
  // - challenges.length < 2 → warning
  // - summary fields < 20 chars → warning
  // - nextSprintFocus empty → warning
  // - sprint focus title > 100 chars → warning
  // - coachNotes < 10 chars → warning
}
```

Business validation issues are categorized as "error" or "warning". Currently all business checks are warnings — none are fatal errors. This can be adjusted as the system matures.

### Two validation entry points:

1. `validateReportOutput(output)` — Strict mode, throws on business errors
2. `validateReportOutputWithWarnings(output)` — Returns both output and business issues

## 8. Provider Health Improvements

### Before:
```typescript
health(): Promise<boolean>
```

### After:
```typescript
interface ProviderHealthResult {
  healthy: boolean;
  provider: string;
  model: string;
  checks: {
    apiReachable: boolean;
    modelExists: boolean;
    apiKeyValid: boolean;
  };
  error?: string;
  checkedAt: string;
}

health(): Promise<ProviderHealthResult>
```

### NVIDIA Implementation:

The health check now performs 3 distinct checks:

1. **API Reachable**: Calls `GET /v1/models` and checks if the endpoint responds
2. **API Key Valid**: Checks for 401/403 status codes indicating authentication failure
3. **Model Exists**: Parses the models list and verifies the configured model is available

Returns granular health information instead of a simple boolean, enabling:
- Targeted error messages ("API key expired" vs "model not found" vs "API unreachable")
- Dashboard health indicators per check
- Automated alerting on specific failure modes

### AIGenerationLogger

```typescript
class AIGenerationLogger {
  log(entry: AIGenerationLogEntry): void;
  logGenerationStart(provider, model, sessionId?): void;
  logPromptBuilt(promptSize, wordCount): void;
  logProviderCall(provider, model): void;
  logResponseReceived(model, responseSize, durationMs, tokens?): void;
```

### Logged Events:
- `generation.start` — Pipeline started

- `generation.validation_complete` — Validation result and duration

- `generation.error` — Error with message

### Security:
- Never logs API keys
- Automatically redacts patterns: `nvapi-*`, `Bearer *`, `api_key: *`

### Configuration:
- Enabled by default in development (`NODE_ENV === "development"`)
- Can be manually enabled/disabled via constructor parameter

## 3. ReportRecord Schema

```typescript
type ReportStatus = "draft" | "reviewing" | "approved" | "published" | "archived";

interface ReportRecord {
  id: string;                    // Unique identifier
  studentId: string;             // Student reference
  sessionId: string;             // Session reference
  version: number;               // Incremental version number
  status: ReportStatus;          // Current lifecycle status
  createdAt: string;             // ISO timestamp
  updatedAt: string;             // ISO timestamp
  generatedBy: string;           // "ai" (future: coach name)
  reportOutput: ReportOutput;    // Validated AI output
  promptVersion: string;         // Prompt template version used
  provider: string;              // LLM provider name
  model: string;                 // LLM model identifier
  confidence: number;            // AI confidence score (0-1)
  sourceCoverage: number;        // Ratio of available/total sources
  generationDuration: number;    // Total pipeline duration in ms
}
```

### Status Lifecycle

```
Generate → Draft → Review → Approved → Published
                     ↓
                  Archived
```

This sprint implements only the **Draft** stage. Future sprints will implement:
- `reviewing` — Coach begins review
- `approved` — Coach approves the draft
- `published` — Report shared with student/parents
- `archived` — Report archived (read-only)

## 6. Versioning Strategy

Every generation creates a **new version**. Previous versions are never overwritten.

```typescript
// In createDraft():
const existingDrafts = await listSessionReports(sessionId);
const nextVersion = existingDrafts.length > 0
  ? Math.max(...existingDrafts.map((r) => r.version)) + 1
  : 1;
```

### Version History

For a session with 3 generations:
- Version 1: First generation
- Version 2: Second generation (after "Generate Again")
- Version 3: Third generation

All versions are stored in the repository and can be retrieved via `getReportVersionHistory(sessionId)`.

### Latest Draft

The workspace always loads the **latest version** for the session:

```typescript
const latestDraft = await getLatestDraftForSession(sessionId);
```

| `promptVersion` | string | Prompt template version (e.g., "1.0.0") |
| `generationDuration` | number | Total pipeline duration in ms |
| `confidence` | number | AI confidence score (0-1) |
| `sourceCoverage` | number | Ratio of available/total sources (0-1) |

### Source Coverage Calculation

```typescript
const sourceCoverage = prompt.metadata.availableSources.length /
  (prompt.metadata.availableSources.length + prompt.metadata.missingSources.length);
```

This measures how much of the expected data was available when generating the report.

## 5. SessionBrief Schema

```typescript
import { z } from "zod";

export const SessionBriefSchema = z.object({
  currentSituation: z.string().min(1),
  progressSinceLastSession: z.string().min(1),
  risks: z.array(z.string().min(1)),
  opportunities: z.array(z.string().min(1)),
  recommendedDiscussionTopics: z.array(z.string().min(1)),
  recommendedActions: z.array(z.string().min(1)),
  coachChecklist: z.array(z.string().min(1)),
  confidence: z.number().min(0).max(1),
});

export type SessionBrief = z.infer<typeof SessionBriefSchema>;
```

### Schema Design Decisions

- **currentSituation**: Concise summary of the student's current state
- **progressSinceLastSession**: What changed since the last session
- **risks**: Array of specific risks or concerns (min 1 required by business validation)
- **opportunities**: Array of positive developments (min 1 required by business validation)
- **recommendedDiscussionTopics**: Topics the coach should discuss (min 1 required)
- **recommendedActions**: Concrete actions for the coach (min 1 required)
- **coachChecklist**: Items to verify or remember during the session
- **confidence**: 0-1 score reflecting analysis reliability

## 6. Validation Flow

```
Raw LLM Response
       ↓
JSON.parse() → SessionBriefValidationError if invalid
       ↓
SessionBriefSchema.safeParse() → Zod errors if schema mismatch
       ↓
Business Validation → Errors if:
  - risks array empty
  - opportunities array empty
  - recommendedDiscussionTopics empty
  - recommendedActions empty
  - confidence < 0.5
       ↓
Typed SessionBrief returned
```

### Reused Infrastructure

- `SessionBriefValidationError` class (same pattern as `ValidationError` in Report Engine)
- Zod for schema validation
- Same error accumulation pattern
- Same `aiLogger` for structured logging
