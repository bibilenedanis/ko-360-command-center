# Final Report: Student Client-Side Navigation Loading Fix

## 1. Affected Student Route

**File:** `src/routes/students_.$studentId.tsx`  
**Route path:** `/students_/$studentId`  
**Route name:** Student 360 / Student Profile Page

## 2. Root Cause

The route loader was calling `getStudentProfileData(params.studentId)` directly from `@/lib/students/profile.server` without wrapping it in a `createServerFn`. This caused a **server/client boundary violation** during client-side navigation.

The `.server.ts` module imports server-only dependencies (Notion API, environment variables) that are not available in the client execution context. During client-side navigation, the loader attempted to execute server-only code without proper server boundary isolation.

## 3. Why Hard Refresh Worked

During hard refresh (initial page load), TanStack Start performs **server-side rendering (SSR)**:
- The loader executes in a full Node.js server context
- All `.server.ts` modules and environment variables are available
- `getStudentProfileData()` can access Notion API and config without issues
- The page renders successfully on the server and hydrates on the client

## 4. Why Client-Side Navigation Failed

During client-side navigation (e.g., clicking a student link from the students list):
- TanStack Start attempts to re-run the loader in the client context
- Without `createServerFn` wrapper, the loader doesn't properly establish the server boundary
- The `.server.ts` module import chain tries to execute in a context where server-only dependencies are unavailable
- This causes the loader to fail or return incomplete data
- The page either shows an error state or loads with missing data

## 5. Same as Session Workspace Bug?

**Yes, this is the exact same pattern.**

Both routes had loaders that directly called `.server.ts` functions without `createServerFn` wrappers:

**Session Workspace (previously fixed):**
```typescript
loader: async ({ params }) => {
  return await getSessionWorkspaceData(params.sessionId);  // ❌ Direct call
}
```

**Student Profile (just fixed):**
```typescript
loader: async ({ params }) => {
  return await getStudentProfileData(params.studentId);  // ❌ Direct call
}
```

Both were fixed by wrapping the server function call in `createServerFn`.

## 6. Exact Fix Applied

Added a `createServerFn` wrapper for the student profile data loader:

```typescript
const loadStudentProfile = createServerFn({ method: "GET" })
  .validator((data: unknown) => {
    if (!data || typeof data !== "object" || !("studentId" in data) || typeof data.studentId !== "string") {
      throw new Error("Invalid studentId");
    }
    return data as { studentId: string };
  })
  .handler(async ({ data }) => {
    return await getStudentProfileData(data.studentId);
  });
```

Updated the route loader to call the server function:

```typescript
loader: async ({ params }) => {
  return await loadStudentProfile({ data: { studentId: params.studentId } });
}
```

This ensures proper server/client boundary isolation during both SSR and client-side navigation.

## 7. createServerFn Added/Changed

**Added:** `loadStudentProfile` server function  
**Method:** GET  
**Validator:** Validates that `studentId` is a non-empty string  
**Handler:** Calls `getStudentProfileData(data.studentId)`  
**Pattern:** Matches the existing pattern used in `sessions_.$sessionId.tsx` and other routes

6. **Generate Parent Version** — Transform to parent-friendly language
7. **Generate Student Version** — Transform to student-friendly language

```typescript
if (!studentId) {
  throw new Error(`No student associated with session: ${sessionId}`);
}

// Failed to fetch sessions
if (!sessionsResult.ok) {
  throw new Error(`Failed to fetch sessions: ${sessionsResult.message}`);
}
```

Graceful handling for missing optional data:
- Returns `null` for missing assessment
- Returns `null` for missing sprint
- Returns empty arrays for missing goals/tasks/recommendations
- Never throws for missing optional data

## 3. Prompt Architecture

The Prompt Builder layer converts a `ReportContext` into a complete `PromptDocument` that can be sent to any LLM provider.

### Architecture Principles

1. **Provider-Independent**: No references to OpenAI, Anthropic, Gemini, or any specific LLM provider
2. **Modular**: Each prompt section is built by a separate function
3. **Template-Driven**: Long prompt strings are stored in templates, not hardcoded in logic
4. **Composable**: Sections can be added, removed, or reordered without changing the builder
5. **Typed**: All prompt components have strict TypeScript types

### Core Types

```typescript
interface PromptDocument {
  system: string;      // System message that sets AI behavior
  user: string;        // User message containing context and request
  metadata: PromptMetadata;
  sections: PromptSection[];  // Individual sections for debugging
}

interface PromptMetadata {
  generatedAt: string;
  templateVersion: string;
  availableSources: string[];
  missingSources: string[];
  characterCount: number;
  wordCount: number;
}
```

## 4. Prompt Generation Flow

```
buildReportPrompt(context: ReportContext)
    ├── 1. Build individual sections
    │   ├── buildRoleSection(context)
    │   ├── buildStudentSection(context)
    │   ├── buildSessionNotesSection(context)
    │   ├── buildAssessmentSection(context)
    │   ├── buildGoalsSection(context)
    │   ├── buildSprintSection(context)
    │   ├── buildTasksSection(context)
    │   ├── buildRecommendationsSection(context)
    │   ├── buildDataAvailabilitySection(context)
    │   └── buildOutputSection()
    ├── 2. Sort sections by order
    ├── 3. Build system prompt from SYSTEM_PROMPT template
    ├── 4. Concatenate all sections into user prompt
    ├── 5. Build metadata (timestamp, word count, sources)
    └── 6. Return PromptDocument { system, user, metadata, sections }
```

## 5. Prompt Section Hierarchy

The prompt is organized into 10 sections, each with a specific purpose:

| Order | Section ID | Title | Purpose |
|-------|-----------|-------|---------|
| 1 | role | Role & Context | Defines the AI's role and coaching context |
| 2 | student | Student Profile | Student demographics and attention status |
| 3 | session-notes | Session Notes | Wins, challenges, core notes, commitments |
| 4 | assessment | Assessment Data | Latest assessment scores and results |
| 5 | goals | Goals | Active and completed goals with progress |
| 6 | sprint | Sprint Data | Current sprint focus and progress |
| 7 | tasks | Tasks | Overdue, upcoming, and completed tasks |
| 8 | recommendations | AI Recommendations | High-risk and pending recommendations |
| 9 | data-availability | Data Availability | Lists available and missing data sources |
| 10 | output-instructions | Output Instructions | Report structure and formatting rules |

## 6. Template Organization

All static prompt text is stored in `prompt.templates.ts`:

- **SYSTEM_PROMPT**: Defines AI behavior, critical rules, and tone (1,200+ characters)
- **ROLE_DEFINITION**: Coaching context and report audience
- **COACH_STYLE**: Strengths-based approach, evidence-based observations, growth mindset
- **REPORT_STYLE**: Structure, language, tone guidelines
- **OUTPUT_FORMAT**: Required report sections (Executive Summary, Strengths, Challenges, etc.)
- **GENERAL_RULES**: Data integrity, confidentiality, professionalism, clarity, actionability
- **PROMPT_TEMPLATE_VERSION**: "1.0.0" for tracking changes

### Template Design Principles

1. **Explicit Constraints**: Never invent facts, use only supplied data, never diagnose
2. **Professional Tone**: Educational coach, not psychologist
3. **Evidence-Based**: Ground all statements in provided data
4. **Growth-Focused**: Frame challenges as opportunities
5. **Actionable**: Every insight leads to concrete next steps
